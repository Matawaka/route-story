## Recommendation: Swiss Alpine road corridor

Prefer a short Gletsch/Furka-area corridor, with a separately sourced/licensed Swiss GPX or explicitly synthetic geometry in its own geographic location. [SWISSIMAGE](https://www.swisstopo.admin.ch/en/orthoimage-swissimage-10) is orthorectified RGB, EPSG2056, native10cm or25cm depending on area; a10cm output raster alone does not prove10cm source acquisition. [swissALTI3D](https://www.swisstopo.admin.ch/en/height-model-swissalti3d) provides0.5m/2m grids in LV95/LN02. The0.5m grid can itself be oversampled; Alpine stereo elevations can have1–3m accuracy. Use ordinary OGD downloads: the product page's separate **sample-data ZIPs are test-only and forbidden in a product**.

[swisstopo OGD conditions](https://www.swisstopo.admin.ch/de/nutzungsbedingungen-kostenlose-geodaten-und-geodienste) allow redistribution, modification and commercial use, with mandatory source attribution. Retain `© swisstopo` visibly in outputs and provenance; this is swisstopo's OGD terms, not an invented CC license. Rendering MP4 derivatives follows those permitted uses (interpretation of the published terms). Do not infer trip date/weather from imagery.

Actual read-only [STAC query](https://data.geo.admin.ch/api/stac/v1/collections/ch.swisstopo.swissimage-dop10/items?bbox=8.35,46.56,8.37,46.58&limit=100) returned, among other intersecting tiles, `swissimage-dop10_2023_2671-1159`, extent `[8.3648975,46.5783993,8.3780983,46.5875011]`, available0.1m and2m EPSG2056 COGs. Provider SHA256 for the0.1m asset: `a680e0a0d11f43fae312ae3aa82766c5cf543f24af9eb84f3ed0b96a508d2327` (decoded from STAC multihash prefix1220; **not independently downloaded/hashed**). STAC's2023 year timestamp is not a verified exact capture day or native10cm acquisition. Actual [DEM query](https://data.geo.admin.ch/api/stac/v1/collections/ch.swisstopo.swissalti3d/items?bbox=8.35,46.56,8.37,46.58&limit=100) returned2025 tiles with0.5m/2m COGs; example `2670-1159` is adjacent, not proof of the complete intended road-corridor intersection. ## Calculated budgets, not measured package sizes

One2048² image at native10cm covers204.8m; at25cm512m; at0.6m1228.8m. Such a square alone exceeds the existing aggregate3million-pixel cap. One1400² detail square plus1000² overview is2.96million pixels: detail coverage140m /350m /840m respectively. Decoded RGBA is11.84MB, complete GPU mip chains approximately15.8MB, **analytical allocation, not VRAM measured on a device**. JPEG output depends on actual terrain/quality: plan a0.3–1.5MiB1400² photo plus0.1–0.5MiB overview, then measure; this estimate is no guarantee of the2MiB aggregate cap. Source COGs can be much larger and must remain developer-only.

A251k-vertex,2m DEM square (501²) covers1km with502002B int16 grid, within existing grid bytes/mesh count, but the loader currently rejects spacing below10m and is fixed to the reviewed Norwegian pack. At0.5m the same1km extent needs~4million vertices, outside bounds; a701² patch covers350m and982802B, leaving almost no additional mesh capacity. Current integer-metre storage also loses sub-metre vertical precision. Changing quantization/vertical datum/source validation is a separate reviewed design, not a silent replacement of Norwegian heights.

Upper-limit mesh attributes/index/UV can approach34MB before driver copies; two bounded photographic textures add~16MB and a256² marker~0.35MB with mips. Whole browser/encoder RAM and actual GPU memory require device measurements. GPU texture size support alone does not prove a device can sustain those allocations.

For a very short Swiss shot, resample imagery to0.5–1m output GSD according to the actual720p footprint and keep both levels fully resident. A longer mountain-road flight cannot retain native10/25cm detail with one1400² patch. It needs a bounded regional texture atlas or paged LOD, exact geographic transforms/feathered boundaries, frustum selection, a known resident set per export shot, and readiness/error barriers before encoding. Do not add network tile loading during export. Preliminary engineering estimate:1–2days crop/provenance/visual proof,3–5days bounded LOD+terrain-seam/readiness work,1–2days device/export validation; estimates, not commitments. Separate package-budget approval and actual measured export are needed before publication.
